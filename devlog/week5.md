## 2. 크롤러가 가진 위험과 판단 로직

### 2-1. 위험은 원인이 다르지만 결과는 같다

크롤러가 위협받는 경로는 세 가지입니다.

- **봇으로 탐지되어 차단당함**
- **학교가 사이트를 개편함** 
- **파싱 로직이 실제 구조와 안 맞게 됨**

세 가지 원인은 다르지만, 결과적으로 크롤러 안에 나타나는 증상은 똑같습니다. **"페이지는 응답하는데 원하는 데이터를 못 뽑아낸다" 또는 "아예 응답이 없다."** 그래서 원인마다 따로 대응책을 만들기보다, **증상 하나를 정확히 감지하는 장치 하나**에 투자하는 게 효율적이라고 판단했습니다.

### 2-2. 지금 크롤러가 이미 갖고 있던 신호를 활용한다

크롤러는 매 사이클마다 이미 이런 로그를 남기고 있습니다.

```
rows found: 11
links extracted: 10
```

- `rows found` = 게시판 페이지에서 파싱된 행(`<tr>`) 개수 → "페이지가 정상적으로 열렸는가"
- `links extracted` = 그중 **링크 파싱(제목+URL 추출)에 성공한 행 개수** → "우리 파싱 로직이 여전히 유효한가"

중요한 점은, `links extracted`는 **"새로 저장된 공지 개수"가 아니라는 것**입니다. 코드상 이미 DB에 있는 예전 글이어도 파싱 자체(제목/URL 뽑기)는 매번 시도되고 성공하면 카운트됩니다. 즉 **새 글이 있든 없든 평소엔 이 값이 거의 일정하게 유지되는 게 정상**입니다. 이 두 숫자의 비율(`links extracted / rows found`)을 **extraction_rate**라고 정의했습니다.

### 2-3. 판단 기준은 "0건이냐"가 아니라 "평소 대비 급락했냐"

`links extracted`가 "새 글 개수"가 아니라 "파싱 성공 건수"이기 때문에, 이 값이 평소 대비 급락하는 건 **"새 글이 없다"가 아니라 "파싱 로직이 더 이상 유효하지 않다"는 신호로 봐도 됩니다.**

| 상황 | rows found | links extracted | 해석 |
|---|---|---|---|
| 평소 | 11 | 10 (약 91%) | 정상 (새 글 유무와 무관하게 파싱은 계속 성공) |
| 구조가 깨짐 | 11 | 0 | **이상** (페이지는 열리는데 셀렉터가 더 이상 안 맞음) |
| 사이트 접근 자체가 막힘 | 0 (또는 연결 실패) | 0 | **이상** (페이지 자체가 안 열림) |

한 번의 결과만으로 판단하지 않고, **직전 여러 사이클의 평균 extraction_rate와 비교**해서 급락 여부를 판단합니다. 이렇게 하면 "새 글이 있었는지"와 무관하게 순수하게 파싱 로직의 건강 상태만 볼 수 있어서, 오탐 가능성이 줄어듭니다.

### 2-5. 별도로 구분해야 할 것: "파싱 성공 건수"와 "신규 저장 건수"

여기서 한 가지 놓치면 안 되는 게 있습니다. **크롤러 자가진단(위 로직)에 쓰는 지표는 "파싱 성공 건수"여야 하고, 나중에 푸시 알림을 트리거할 때 쓸 지표는 "실제로 새로 저장된 공지 개수"여야 한다는 점**입니다. 이 둘을 섞으면, 이미 저장된 예전 글까지 "신규"로 착각해서 알림이 중복으로 쌓이는 문제가 생길 수 있습니다. 지금 코드는 `saveIfNew` 안에서 "Saved new notice" 로그만 남기고 이 개수를 별도로 집계하지 않는데, 다음 주 `crawl_log` 설계 시 **`links_extracted`(파싱 성공, 건강 체크용)와 `newly_saved_count`(신규 저장, 알림 트리거용)를 서로 다른 컬럼으로 분리**해서 기록할 계획입니다.

### 2-6. 아직 못 정한 것

**표본이 너무 적을 때(rows found가 1~2개)** extraction_rate가 우연히 크게 튈 수 있습니다. 최소 표본 크기 이하일 때는 판단을 보류하는 규칙도 추가로 필요합니다.

## 3. 스케줄러 주기

실제로 관찰해보면 공지 게시 빈도는 일정하지 않습니다. 어떤 날은 하루에 2건이 몰려서 올라오기도 하고, 며칠간 새 글이 없기도 합니다. 정확한 평균값을 근거로 삼기엔 데이터가 아직 적어서, 대신 **가장 몰리는 경우(최악의 경우)를 기준으로** 판단했습니다.

| 주기 | 판단 |
|---|---|
| 1분~5분(개발용) | 실제 공지 빈도(하루 최대 2건 수준)에 비해 압도적으로 과도한 요청. 봇 차단 리스크만 키움 |
| **1시간(현재)** | 하루에 여러건이 몰리는 경우에도, 평균적으로 약 30분 안에 반영됨. 최대 지연도 1시간을 넘지 않음 |
| 6시간~하루 1회 | 서버 부담은 최소화되지만, 마감 임박 공지를 최대 하루 늦게 받을 수 있어 서비스 핵심 가치와 충돌 |

**가장 공지가 몰리는 날을 기준으로 계산해도 1시간 주기면 충분히 빠르게 반영**되면서, 서버에 주는 부담(하루 24회)도 합리적인 수준이라 판단해 유지했습니다. 다만 이건 게시판 2개 기준이고, 게시판이 수백 개로 늘어나면 "전체 사이클이 1시간을 넘지 않게" 배치 처리로 재설계해야 한다는 한계도 인지하고 있습니다.

## 4. 앞으로의 구현 방향

1. `crawl_log` 테이블에 `rows_found`, `links_extracted`, `success`, `error_message`를 사이클마다 기록
2. extraction_rate 계산 및 급락 판단 로직 구현 (임계치는 데이터 축적 후 확정)
3. Spring Boot Actuator 커스텀 HealthIndicator로 `/actuator/health`에 상태 노출
4. 이상 감지 시 Discord 웹훅으로 알림 발송 (게시판명, 직전 extraction_rate, 마지막 성공 시각 포함)
5. 파서 스냅샷 테스트(저장된 HTML로 파싱 로직 검증) — 단, 이건 실시간 사이트 변경 감지가 아니라 **제가 코드 수정 중 실수로 기존 게시판을 망가뜨리는 걸 막는 회귀 테스트** 용도임을 구분해서 인지하고 있음
6. `board_crawl_config`(설정 기반 파서 관리) 구조와 연결해, 게시판 1개 추가 시 코드 수정 없이 설정 추가만으로 끝나는 것이 최종 목표

## 5. 흐름 정리 

### 크롤링 → 자가진단 → 알림 파이프라인
실선(구현 완료) / 괄호(설계·예정)

```
Scheduler (1시간 주기)
  → CrawlerService: 게시판 HTML 파싱 (rows found / links extracted)
  → 중복 검사 (board_id + external_id)
  → 신규 공지 DB 적재                                        

  (→ crawl_log에 이번 사이클 결과 기록)
  (→ 직전 N회 평균과 비교해 extraction_rate 급락 여부 판단)
  (→ 이상 감지 시 Discord 웹훅 알림)
  (→ 신규 공지 → 구독 키워드 매칭 → 푸시 발송 → 유저 앱 수신)  
```
