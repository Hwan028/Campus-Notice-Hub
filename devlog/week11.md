## 1. 전체 흐름: 공지 본문에서 캘린더까지

```
크롤러가 새 공지 저장 ─┐
                       ├→ [2분마다] 상세 페이지 읽기 → Gemini → 서버 검증 → 공지에 기간 저장
앱에서 공지 저장 ──────┘                                                        │
                                                                                  ▼
                         앱 저장 탭 캘린더 ◀── 저장 목록 + 기간 ◀── GET /api/scraps
```

- 지난주 "고민"에서 정한 **AI 추출 + 검증** 방향을 실제로 구현했습니다.
- 크롤·푸시와 완전히 분리해서, AI가 느리거나 멈춰도 공지 수집과 알림은 영향이 없습니다.

## 2. AI 선정: Gemini

| 기준 | Gemini Flash Lite | 다른 회사 소형 모델 |
|---|---|---|
| 무료 사용 | 있음 (하루 500회) | 사실상 유료 |

## 3. 기간 추출 방식

**Gemini에 보내는 것**: 규칙 + 제목 + 게시일 + 본문 텍스트(최대 6,000자) + 본문 이미지(최대 3장)

| 규칙 | 이유 |
|---|---|
| 실제로 적힌 날짜만, 추측 금지 | 지어내기 방지 |
| 신청·접수·모집 기간 우선, 없으면 행사일 | 학생이 챙길 날짜가 먼저 |
| 게시일·전화번호·"2026학년도 2학기"는 기간 아님 | 자주 헷갈리는 날짜 제외 |
| 연도 생략 시 게시일 기준 | `11. 22.(일)` 같은 표기 대응 |
| 마감만 있으면 시작 = null | `~ 11.20.(금) 10:00까지` 대응 |
| 근거 문구를 원문 그대로 복사 | 서버 검증용 |
| 다른 일정이 더 있으면 표시 | "다른 일정 있음" 배지 |
| 기간이 없으면 found=false | 억지로 만들 이유를 없앰 |

```
{ "candidates": [ { "content": { "parts": [
    { "thought": true, "text": "(생각 과정)" },
    { "text": "{\"found\":true,\"label\":\"신청기간\",\"start\":\"2026-11-18\",\"end\":\"2026-11-26\",
               \"evidence\":\"신청기간 : 2026.11.18(수) ~ 11.26(목) 17:00까지\",
               \"fromImage\":false,\"hasMorePeriods\":false}" }
] } } ] }
```

**2차 검증 (`PeriodValidator`)**

| 결과 | 조건 | 캘린더 |
|---|---|---|
| CONFIRMED | 근거 문구가 **실제 본문에 있음** | 표시 |
| ESTIMATED | 이미지에서 읽어 원문 대조 불가 | 표시 ("이미지 추정") |
| NOT_FOUND | 기간 없는 공지 | 표시 안 함 |
| REJECTED | 근거가 본문에 없음 / 시작 > 끝 / 게시일과 너무 먼 날짜 | 표시 안 함 |

- 원칙: **확실하지 않으면 보여 주지 않는다.** 틀린 날짜를 보여 주는 것보다 빠뜨리는 쪽을 택했습니다.

## 4. 정확도 실험

관리자 API(`POST /api/admin/period/experiment`)로 최근 공지 20개를 돌리고, **원문과 하나씩 비교해 직접 채점**했습니다.

| 항목 | 결과 |
|---|---|
| 정확도 | **19 / 20 (95%)**, 틀린 날짜 **0건** |
| 텍스트 공지 | 11개 중 10개 맞음, 1개 애매 |
| 이미지만 있는 공지 | 5개 중 5개 맞음 |
| 기간 없는 공지 판정 | 4개 중 4개 맞음 |
| 속도 | 공지당 평균 6.8초 |

**애매했던 1건 → 설계 변경으로 이어짐**
- 예비군 공지에 일정이 3개(기본훈련, 2차 보충, 32시간 초과자 보충)처럼 여러개의 일정인것.
- 선택지: A. 하나만 / B. 여러 개 저장 / **C. 대표 기간 + "다른 일정 있음" 표시**
- **C를 선택**: DB 구조를 단순하게 유지하면서, 사용자가 원문을 확인하도록 안내합니다.

## 5. 백그라운드 처리

| 값 | 근거 |
|---|---|
| **2분마다** 확인 | 크롤이 1시간마다라 새 공지 입장에선 2분 지연은 무시할 수준. 일이 없으면 DB 조회 1번뿐 |
| 한 번에 **10개**, 1.5초 간격 | 공지당 평균 6.8초 → 10개 ≈ 70초로 2분 안에 끝나 실행이 겹치지 않음. 학교 서버 배려 |
| 실패 시 **최대 3번** | 실험에서 본 실패는 모두 일시적(혼잡·시간 초과). 영구 실패를 끝없이 반복하지 않게 |
| 하루 **300개** 상한 | 무료 한도 하루 500회의 60% → 재시도 여유 확보. 실제 사용량은 하루 20회 안팎이라 **버그로 인한 폭주 방지**용 |
| 최근 **3일** 새 공지 | 서버가 주말 동안 꺼져 있어도 복구 후 놓치지 않게. 그보다 오래된 공지는 저장된 것만 |

- AI 호출은 트랜잭션 밖에서, 결과 저장만 짧은 트랜잭션으로 합니다. (AI가 3분 걸려도 DB 연결을 잡고 있지 않도록)
- 공지당 **한 번만** 분석하고 결과를 저장 → 비용은 사용자 수가 아니라 새 공지 수에 비례합니다.

## 6. 저장 탭 캘린더

| 요소 | 내용 |
|---|---|
| 월 달력 | 저장한 공지의 기간을 **색 줄**로 표시. 공지마다 색이 다르고, 이미지 추정은 연하게 |
| 겹치는 기간 | 같은 공지는 한 달 내내 같은 높이 줄에 오도록 배치 |
| 날짜 선택 | 그날 걸친 일정만 목록에 표시 |
| 아래 시트 | 쓸어 올려 3단계(접힘·반·전체). 마감 가까운 순, 지난 일정은 흐리게 |
| 목록 한 줄 | 라벨(신청기간 등) · 기간 · D-day · "다른 일정 있음" · "이미지 추정" → 누르면 원문 |
| 요약 | "마감 임박 n" · "기간 분석 중 n" · "기간 없는 공지 n" |
| 새로고침 | 분석 중이면 20초마다 자동(최대 4분), 달력을 당겨서 수동 |

![저장 탭 캘린더](../images/calendar.png)

- 요약 표시는 "5개 저장했는데 캘린더엔 3개만 있네, 고장인가?"를 막기 위한 것입니다. 왜 안 보이는지(분석 중 / 기간 없음)를 알려 줍니다.
- 저장 목록 화면에도 서버가 분석한 마감일로 D-day가 나옵니다.
